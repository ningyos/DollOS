# Qwen3.6 Usage Best Practices for DollOS
*Research date: 2026-05-07 | Model: unsloth/Qwen3.6-35B-A3B-GGUF:UD-Q4_K_XL via llama-server*

---

## 1. TL;DR — 5 Actionable Items (Ordered by Impact)

1. **Add `presence_penalty 1.2–1.5` to the llama-server sampling flags.** The repetition symptom ("我很好！主人呢？我很好！主人呢？") is the exact failure mode Qwen team calls out for thinking mode. The official fix is `presence_penalty` (0–2 range). This is the single highest-impact change.

2. **Your tool call format is correct — but the tool definition block must follow the exact Qwen3 template wording.** The native format is `<tool_call>{"name": X, "arguments": {...}}</tool_call>` after `</think>`. DollOS already uses this. However, the template boilerplate before `<tools>` must match: *"You may call one or more functions… function signatures within `<tools></tools>` XML tags… return a json object… within `<tool_call></tool_call>` XML tags."* If DollOS is using different header text, the model may not reliably emit tool calls.

3. **Your sampling params are exactly correct for thinking mode.** `temp=0.6 top_p=0.95 top_k=20 min_p=0.00` matches the official recommendation verbatim. No change needed here.

4. **Do not inject ReAct-style labels into the `<think>` block prefix.** The current DollOS prefill uses `STATE:\n...\nRECALL:\n...\nDECISION: ` — the `DECISION:` label at the end is a stopword-style pattern. Qwen docs explicitly warn this interferes with thinking-mode reasoning. Replace the dangling `DECISION: ` with prose context or drop the final label.

5. **`--reasoning-format none` is correct and required for prefill.** This flag makes llama.cpp leave `<think>...</think>` content unparsed in `message.content`, which is the only mode that allows DollOS's `/completion` prefill injection to work without the server stripping or re-parsing the block.

## 2. Sampling Parameters

### Official Recommendation (Thinking Mode)

| Parameter | Official Value | DollOS Current | Status |
|---|---|---|---|
| `temperature` | 0.6 | 0.6 | ✅ Correct |
| `top_p` | 0.95 | 0.95 | ✅ Correct |
| `top_k` | 20 | 20 | ✅ Correct |
| `min_p` | 0 | 0.00 | ✅ Correct |
| `presence_penalty` | 0–2 (recommended when repetition occurs) | **not set** | ⚠️ Missing |
| Greedy decoding | Explicitly forbidden | Not used | ✅ Fine |

### Official Warning on Greedy Decoding

From the Qwen3-30B-A3B model card (HuggingFace):
> "DO NOT use greedy decoding, as it can lead to performance degradation and endless repetitions."

DollOS uses sampling (`temp=0.6`) so this is not a risk, but it confirms the repetition symptom is a known failure mode of under-sampling, not a model flaw per se.

### Presence Penalty

The official card says `presence_penalty` in the 0–2 range reduces repetitions but "may occasionally result in language mixing and a slight decrease in model performance." For DollOS with Japanese/Chinese character responses, a conservative value of **1.2–1.5** is recommended. Values above 1.8 risk language-mixing artifacts in multi-lingual output.

*Source: [https://huggingface.co/Qwen/Qwen3-30B-A3B](https://huggingface.co/Qwen/Qwen3-30B-A3B)*

### Non-Thinking Mode (for reference)

If DollOS ever disables thinking: `temp=0.7 top_p=0.8 top_k=20 min_p=0`. Note the lower `top_p` and higher temperature compared to thinking mode.

## 3. Thinking Block Expectations

### What Qwen3 Wants Inside `<think>`

The model was trained with **free-form internal monologue** in the `<think>` block. No structural format is imposed by the training data. The model itself produces varied styles — step-by-step reasoning, deliberation, scratch-pad math, etc.

### Anti-Pattern: ReAct Labels

The Qwen3 function calling documentation explicitly states:
> "It is not recommended to use tool call templates based on stopwords, such as ReAct, due to potential unexpected behavior."

The concern is that stopword-anchored formats (THOUGHT: / ACTION: / OBSERVATION:) in the `<think>` block conflict with the model's trained free-form reasoning style and cause the model to imitate the prompt structure rather than reason genuinely. This directly explains the DollOS symptom: `THOUGHT: ... ACTION: ... REPLY:` plaintext labels in `<think>` output.

**Root cause**: If DollOS's prefill or system prompt contains ReAct-style labels, the model will mirror them. Even injecting `DECISION: ` at the end of the prefill provides a stopword signal that can trigger label-following behavior.

*Source: [https://qwen.readthedocs.io/en/latest/framework/function_call.html](https://qwen.readthedocs.io/en/latest/framework/function_call.html)*

### What DollOS Currently Injects

```
STATE:
{summary}

RECALL:
{...}
DECISION: 
```

The `STATE:` and `RECALL:` headers are neutral prose labels — acceptable. The dangling `DECISION: ` at the end is a stopword anchor and should be removed or replaced with a prose continuation like: *"Based on the above context, I should now"* — or simply omitted so the model's thinking is unconstrained.

### Token Boundary Note

The `</think>` closing token has ID `151668`. When DollOS prefills inside `<think>`, the continuation runs until the model emits this token naturally. No special handling needed beyond ensuring the prefill does not itself contain `</think>`.

### Multi-Turn History

Official guidance: **do not include thinking content in conversation history.** Only the final output (after `</think>`) should appear in `assistant` turns in the history. This is already handled by Qwen's Jinja2 template when using the chat API, but since DollOS uses raw `/completion`, it must manage this manually. Including `<think>...</think>` in prior turns will inflate context and may confuse the model about what counts as "already decided."

*Source: [https://huggingface.co/Qwen/Qwen3-30B-A3B](https://huggingface.co/Qwen/Qwen3-30B-A3B)*

## 4. Tool Calling Format

### Qwen3 Native Format (from tokenizer_config.json)

**System prompt preamble** (must appear before `<tools>`):
```
# Tools

You may call one or more functions to assist with the user query.

You are provided with function signatures within <tools></tools> XML tags:
<tools>
[tool definitions as JSON array of objects]
</tools>

For each function call, return a json object with function name and arguments within <tool_call></tool_call> XML tags:
<tool_call>
{"name": <function-name>, "arguments": <args-json-object>}
</tool_call>
```

**Tool definition schema** (each tool):
```json
{
  "type": "function",
  "function": {
    "name": "tool_name",
    "description": "What it does",
    "parameters": {
      "type": "object",
      "properties": {
        "param": {"type": "string", "description": "..."}
      },
      "required": ["param"]
    }
  }
}
```

**Model output format** (tool call after `</think>`):
```
<tool_call>
{"name": "tool_name", "arguments": {"param": "value"}}
</tool_call>
```

**Tool result format** (fed back as user turn):
```
<tool_response>
{result content}
</tool_response>
```

### DollOS Current vs Qwen3 Native

DollOS uses `<tool_call>{"name":"X","arguments":{...}}</tool_call>` — this matches the native format. The critical question is whether the system prompt preamble text matches exactly. If DollOS uses different header text (e.g., a custom instruction block without the exact `"You are provided with function signatures within <tools></tools> XML tags"` wording), the model may not reliably trigger the `<tool_call>` output format.

The **confabulation symptom** (model says "I did X" without emitting a tool call) is consistent with the model understanding it should call a tool but not having the format sufficiently anchored in its context. Matching the exact native preamble text removes this ambiguity.

### Tool Result Wrapping

DollOS currently pipes shell/tool output back to the model. If it is not wrapped in `<tool_response>...</tool_response>` tags (fed as a user-role message in the conversation), the model may misparse it as plain user text, explaining the symptom where Shell dir listing output is interpreted as "no specific output."

*Source: [https://huggingface.co/Qwen/Qwen3-30B-A3B/blob/main/tokenizer_config.json](https://huggingface.co/Qwen/Qwen3-30B-A3B/blob/main/tokenizer_config.json)*

## 5. Prefill Technique

### `--reasoning-format none` — What It Does

From llama.cpp server documentation:
> `--reasoning-format none`: "leaves thoughts unparsed in `message.content`"

The other options (`deepseek`, `deepseek-legacy`) extract reasoning content into a separate `message.reasoning_content` field. With `none`, the entire model output including `<think>...</think>` is returned as a flat string in `message.content`. This is the correct mode for DollOS because:

1. DollOS uses `/completion` (raw completion), not `/chat/completions`. The reasoning-format flag affects `/chat/completions` response parsing. On `/completion`, output is always raw text regardless.
2. DollOS needs to inject content into the `<think>` block as a prefill (the `prompt` field already contains the opening `<think>` plus the VoM RECALL/STATE content). With `--reasoning-format none`, there is no server-side interference with the thinking block structure.
3. If `deepseek` mode were active and `/chat/completions` were used, the server might strip or relocate the injected content.

**Why it's required for prefill to work**: On `/completion`, the `prompt` field is the literal string sent to the model for continuation. DollOS constructs this as the full formatted prompt ending with `<think>\nSTATE:...\nRECALL:...\n`. The model then continues from that point. `--reasoning-format none` ensures no server middleware re-structures this before or after inference.

*Source: [https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)*

### Confirmed Prefill Pattern

The Qwen3 GitHub README confirms llama.cpp usage: `--temp 0.6 --top-k 20 --top-p 0.95 --min-p 0`. No explicit prefill guidance is published by Qwen team, but the token boundary approach (model continues until it emits `</think>` token 151668) is consistent with how llama.cpp raw completion works.

**Community-confirmed working pattern** (from llama.cpp and vLLM community): prepend the generation prompt with `<think>\n` and the model correctly treats subsequent content as its in-progress thought. There is no documented conflict with injecting structured context (STATE/RECALL) here, only the warning against ReAct-style stopword labels.

## 6. Known Issues

### Repetition (Confirmed, Official)

Repetition is a documented failure mode for thinking-mode Qwen3 when `presence_penalty` is not set. The official model card warns against greedy decoding but also recommends `presence_penalty` as the remedy. The DollOS symptom matches exactly.

**Affected**: All Qwen3 thinking models. Not quant-specific.

**Fix**: Add `--presence-penalty 1.3` (or equivalent in the `/completion` request body as `"presence_penalty": 1.3`).

### Confabulation / Ghost Tool Calls

Not specifically documented as a Qwen3 bug, but the tool calling docs implicitly address it: the model must see the exact native preamble to reliably emit `<tool_call>` tokens. Without the anchoring text, the model may narrate its intended action in prose instead of executing it. This is a **prompt engineering issue**, not a model defect.

### ReAct Label Leakage Into `<think>`

The model tends to imitate structural patterns it sees in its context. If the prefill or system prompt contains labeled segments (THOUGHT:, ACTION:, DECISION:), the model echoes these in its generated thinking content. This is not a bug but a **behavioral consequence of the instruct fine-tuning** — the model is trained to be a good format-follower.

### Multi-Step Tool Use Degradation (Official Warning)

From the Qwen3 GitHub README:
> "Due to preprocessing of API requests in SGLang/vLLM, which drops all `reasoning_content` fields, the quality of multi-step tool use with Qwen3 thinking models may be suboptimal."

This does not apply to DollOS (which uses raw `/completion` and manages history manually), but it confirms that **not including prior thinking content in history** can hurt multi-step agentic tasks. For DollOS's Cascade loop, this means the tool result context (what was done, what was returned) needs to be clearly present in the `<tool_response>` turns.

### UD-Q4_K_XL Quant — No Specific Issues Reported

No quant-specific issues were found for `UD-Q4_K_XL`. Unsloth's Dynamic 2.0 quantization is documented as maintaining "SOTA quantization accuracy." The standard issues (repetition, tool calling format sensitivity) apply at all quant levels.

*Sources: [https://huggingface.co/Qwen/Qwen3-30B-A3B](https://huggingface.co/Qwen/Qwen3-30B-A3B), [https://huggingface.co/unsloth/Qwen3-30B-A3B-GGUF](https://huggingface.co/unsloth/Qwen3-30B-A3B-GGUF), [https://github.com/QwenLM/Qwen3/blob/main/README.md](https://github.com/QwenLM/Qwen3/blob/main/README.md)*

## 7. Concrete DollOS Changes

### llama-server flags

- **Add**: `--presence-penalty 1.3` (start here; tune up to 1.5 if repetition persists; stay below 1.8 to avoid language mixing in CJK output)
- **Keep**: all current flags unchanged (`--temp 0.6 --top-p 0.95 --top-k 20 --min-p 0.00 --reasoning-format none --jinja --chat-template-kwargs '{"enable_thinking": true}'`)

### System prompt — tool definition block

Replace whatever preamble currently precedes `<tools>` with the exact Qwen3 native text:

```
# Tools

You may call one or more functions to assist with the user query.

You are provided with function signatures within <tools></tools> XML tags:
<tools>
{{ tools_json }}
</tools>

For each function call, return a json object with function name and arguments within <tool_call></tool_call> XML tags:
<tool_call>
{"name": <function-name>, "arguments": <args-json-object>}
</tool_call>
```

### VoM prefill — remove `DECISION: ` trailing label

Current ending: `...RECALL:\n{...}\nDECISION: `

Change to either:
- `...RECALL:\n{...}\n` (plain, model starts thinking freely), or
- `...RECALL:\n{...}\nWith the above in mind,` (soft prose continuation, no stopword)

Avoid any label that ends with `: ` as this anchors ReAct-style continuation.

### Tool result formatting

Wrap all tool/shell results returned to the model in `<tool_response>` tags in the user-role message:

```
<tool_response>
{actual output here}
</tool_response>
```

This directly addresses the "Shell returns dir listing, model interprets as no specific output" symptom — the model needs the structural signal to know this is a tool result, not user freetext.

### Conversation history — strip `<think>` blocks

Ensure that when building the prompt for subsequent turns, the `<think>...</think>` content from prior assistant turns is **stripped**. Only the final answer (content after `</think>`) should appear in history. If DollOS is already doing this, no change needed. If `<think>` blocks are being included in history, this inflates context and may cause the model to re-reason about already-decided actions.

### Per-request `presence_penalty` (alternative to server flag)

If per-request control is preferred over the server-level flag, include `"presence_penalty": 1.3` in the `/completion` JSON body. This allows adjusting per-event type (e.g., lower for longer creative responses, higher for short reactive replies where repetition is most likely).
